# Agent 工作规则

## 基本约定

- 项目内的 `AGENTS.md`、格式化配置和既有代码风格优先；不要格式化或整理与当前任务无关的代码。
- 注释使用中文；领域术语、标识符和代码片段保留英文。

## 设计与实现

- 保持设计简洁，不要过度抽象，不要有兼容性设施，避免重复代码。
- 避免自由函数（free-function）：先查找并复用已有工具函数；确需新增时，将同一职责的状态和行为组织到合适的 `struct` 中，不要新增零散的自由函数。
- 组合优先于继承。
- 可执行约束优先通过类型、断言和测试表达。

## 设计分析与文档

文档和注释首先服务于后续 Agent 和开发者安全地修改系统：用尽量少、稳定且可验证的信息说明设计约束和变更影响，而不是逐项复制当前代码结构。笔记应简洁清晰、形象易懂、体系化。

### 事实来源

- **当前实现事实**：代码、构建配置、测试和运行结果说明系统现在如何工作；文档不能覆盖这些事实。
- **规范性事实**：人工确认的需求、设计意图和设计不变量说明系统为什么这样设计、合法变化必须保持什么。实现暂时偏离时，应记录偏差，而不是静默降低规范。

### 信息层次与内容分工

进行设计分析、编写文档或补充注释时，应区分三个信息层次：

- **设计理念**：解释为什么这样设计，以及希望长期坚持的方向、职责和取舍。
- **设计不变量**：说明合法变化中必须保持的约束、适用边界和破坏后果。
- **当前实现细节**：说明当前类型、调用、线程、锁、配置或平台机制如何实现设计，允许随内部实现变化。

三层是组织和分析内容的心智模型，不是固定模板；文档、模块 README 和代码注释只承载适合自己的部分，只更新直接承载相应内容的位置。不要引入 invariant ID、YAML、注册表或强制章节，也不要把偶然代码结构、一次性迁移步骤或当前类名直接提升为设计不变量。

## 代码风格与注释

- 新增或修改模块、关键类型和关键状态时，应补充与其复杂度相称的注释，可以详细说明局部且非显然的所有权、生命周期、线程、锁、顺序和失败语义。不要要求每个普通字段都写重复性注释。
- 关键函数和关键分支应解释设计意图、调用契约和选择当前实现的原因，不复述显而易见的代码行为，也不在代码注释中复制模块级或跨模块设计。内容分工遵循本文“设计分析与文档”一节。
- Rust 的 `use` 按标准库、第三方 crate、工作区内其他 crate、当前 crate 分组，组间留空行；项目已有约定优先。
- Rust 和 C/C++ 的多行注释使用连续的 `///`，不使用连续的 `//`。
- Rust 和 C/C++ 字段带有多行注释时，与前一个字段之间保留一个空行。

## 变更与提交

- 将代码改动加工成便于人工 Review 的形式。给出设计方案、修改代码时，按本文“设计分析与文档”区分设计理念、设计不变量和当前实现细节，主动说明保持或改变了哪些重要不变量，以及相应证据和风险，不要求固定的不变量登记格式。
- 无法证明的结论必须标明是推断，不得宣称已经验证。
- 每个提交只能包含一个可验证的行为变化，且必须可独立编译和回滚。
- 优先按语义和风险拆分提交，不以 300 行作为唯一拆分标准；机械性代码应单独提交并明确标注。
- commit 消息格式：`[add/update/xxx] xxx`（中文 + 英文术语）。
