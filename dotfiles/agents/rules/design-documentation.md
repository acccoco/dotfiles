# 设计分析、文档与注释规则

## 核心原则

文档和注释首先服务于后续 Agent 和开发者安全地修改系统：用尽量少、稳定且可验证的信息说明设计约束和变更影响，而不是逐项复制当前代码结构。

需要区分两类事实来源：

- **当前实现事实**：代码、构建配置、测试和运行结果说明系统现在如何工作；文档不能覆盖这些事实。
- **规范性事实**：人工确认的需求、设计意图和设计不变量说明系统为什么这样设计、合法变化必须保持什么。实现暂时偏离时，应记录偏差，而不是静默降低规范。

进行设计分析、编写文档或补充注释时，应区分三个信息层次：

- **设计理念**：解释为什么这样设计，以及希望长期坚持的方向、职责和取舍。
- **设计不变量**：说明合法变化中必须保持的约束、适用边界和破坏后果。
- **偏实现的流程细节**：说明当前类型、调用、线程、锁、配置或平台机制如何实现设计，允许随内部实现变化。

三层是组织和分析内容的心智模型，不是固定模板；不同文档和注释只承载适合自己的部分。不要引入 invariant ID、YAML、注册表或强制章节，也不要把偶然代码结构、一次性迁移步骤或当前类名直接提升为设计不变量。

## 内容放置

- 总结性和架构文档优先记录设计理念、跨边界不变量、核心概念、高层所有权、状态机、失败语义、非目标和取舍，仅保留必要代码入口。
- 模块 README 记录模块为何存在、拥有什么和不拥有什么、依赖方向、线程与生命周期边界、局部不变量以及相关文档入口。
- 代码注释靠近局部实现，可以按复杂度详细解释非显然的设计意图、所有权、生命周期、同步、状态转换和特殊分支，但不重复全局设计或逐行复述代码。
- 操作和排查文档可以保留当前命令、路径、参数、日志和平台细节，但不要把这些内容复制到长期设计文档。
- 类型、断言和测试优先承载可执行约束；文档和注释解释行为背后的设计与约束。

## 工作规则

- 同一个设计理念或不变量只在最合适的位置完整解释，其它位置使用简短摘要和链接。
- 设计、架构或重构分析应识别设计理念、不变量和实现方式，并说明新方案保持或改变了什么，不要求使用固定章节。
- 分析当前系统时结合代码、测试和文档，不把旧计划或过时文档直接当作当前事实。
- Agent 从代码或历史材料总结出的约束只有在得到代码、测试或人工需求证实时，才能写成正式不变量；无法证明的内容必须标明是推断或当前观察。
- 根据变化层次更新最接近的内容 owner：设计理念更新总结性文档，不变量更新其设计或模块文档，实现细节更新代码、注释或操作文档。
- 纯重构且文档仍准确时不制造无意义改动；实现违反既有不变量时记录偏差，不为迁就实现而静默降低设计。
