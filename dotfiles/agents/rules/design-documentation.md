# 设计分析、文档与注释规则

## 核心原则

文档和注释首先服务于后续 Agent 和开发者安全地修改系统：用尽量少、稳定且可验证的信息说明设计约束和变更影响，而不是逐项复制当前代码结构。

需要区分两类事实来源：

- **当前实现事实**：代码、构建配置、测试和运行结果说明系统现在如何工作；文档不能覆盖这些事实。
- **规范性事实**：人工确认的需求、设计意图和设计不变量说明系统为什么这样设计、合法变化必须保持什么。实现暂时偏离时，应记录偏差，而不是静默降低规范。

进行设计分析、编写文档或补充注释时，应区分三个信息层次：

- **设计理念**：解释为什么这样设计，以及希望长期坚持的方向、职责和取舍。
- **设计不变量**：说明合法变化中必须保持的约束、适用边界和破坏后果。
- **偏实现的流程细节**：说明当前类型、调用、线程、锁、配置或平台机制如何实现设计，允许随内部实现变化。

三层是组织和分析内容的心智模型，不是固定模板；不同文档和注释只承载适合自己的部分。不要引入 invariant ID、YAML、注册表或强制章节，也不要把偶然代码结构、一次性迁移步骤或当前类名直接提升为设计不变量。
